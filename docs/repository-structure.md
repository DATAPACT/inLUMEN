# Repository structure

What each top-level folder is for. Each folder has one purpose; a file that does
not fit the purpose of its folder belongs somewhere else.

| Folder | Purpose |
|---|---|
| `backend/` | The gateway API (Flask): pipeline graph, files, chat, deployment artifacts, settings. Its tests are in `backend/tests/`. |
| `frontend/` | The web application (React, Vite). Unit tests sit next to the code, browser tests are in `frontend/e2e/`, and the load-test tool is in `frontend/loadtest/`. |
| `packages/agents/` | The `inlumen-agents` library, published on PyPI: pipeline design agent (`inlumen.design`), code generator (`inlumen.codegen`) and the shared contracts (`inlumen.contracts`). Tests that need only the library are in `packages/agents/tests/`. |
| `codegen/` | The code generation service (FastAPI). It wraps `inlumen.codegen` and validates generated packages. |
| `runner/` | The pipeline runner service, which executes saved pipelines in the background. |
| `shared/` | Small modules used by more than one service. `scripts/sync_shared.py` copies them into the services, and CI checks that the copies match; edit them here, not in the copies. |
| `contracts/` | Published JSON schemas, one folder per contract version (`v2` to `v4`, `task-package-v1`, `plugin-manifest-v1`). The `task-package-v1` and `plugin-manifest-v1` files are generated by `scripts/sync_shared.py` from the library; do not edit them by hand. |
| `examples/` | Example pipelines, Task packages and plugin definitions used by the docs, the development stack and the tests. |
| `evals/` | Evaluation material, one folder per evaluation. See [`evals/README.md`](../evals/README.md). |
| `scripts/` | Operations and CI tooling. See [`scripts/README.md`](../scripts/README.md). |
| `docs/` | Documentation. See the [documentation index](./index.md). |
| `.github/` | CI workflows (tests, container images, deploy) and release notes for GitHub releases. |

## Inside `backend/`

The entry points and cross-cutting helpers stay at the root of `backend/`; everything else is in a package named after its area.

| Package | Contents |
|---|---|
| root | `inlumen_api.py` (the gateway app and entry point), `analytics_api.py`, `public_api.py`, `migrate.py`, `dev_runner.py`, and the helpers every area uses (`runtime_config`, `flask_setup`, `async_runtime`, `local_api_client`, `run_artifact_names`) |
| `auth/` | Authentication, permissions and encrypted secrets |
| `workspaces/` | Workspace records, storage scoping and queries |
| `storage/` | MinIO access, the object API and file validation |
| `graph/` | The Neo4j API, the graph client and graph revisions |
| `export/` | Deployment artifacts, the Argo bundle, runtimes and Task packages |
| `llm/` | LLM configuration, credentials and application-wide LLM settings |
| `chat/` | Chat routes, chat state and conversations |
| `provenance/` | Provenance records and reports |
| `runs/` | Pipeline runner client, code generation runs and run outputs |
| `pipeline_agent/`, `plugins/`, `generators/`, `node_definitions/` | The design agent wiring, plugins, generator routes and node definitions (unchanged) |

Modules are imported by their full path, for example `from graph.neo4j_api import ...`.

## Files at the root

- `docker-compose.yml` and `docker-compose-prod.yml`: the development and production stacks.
- `.env.example` and `.env.production.example`: templates for the two environment files.
- `requirements-test.txt`: installs the backend, the agents library and the codegen service for local test runs.

## Where a new file goes

- **A test** goes with the code it imports: library-only tests in `packages/agents/tests/`, service tests in that service's `tests/` folder.
- **A script** that operates or checks the system goes in `scripts/`; a script that scores or runs an evaluation goes in `evals/<name>/scripts/`.
- **Run outputs, model files and local state** are not committed. The ignore rules cover `state/`, `outputs/`, `evals/*/results/` and `evals/*/models/`.
