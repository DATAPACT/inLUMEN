# InLumen Deployment Validation

Standalone validation harness for deployment bundles generated by InLumen.

It validates:

- canonical bundle structure
- Argo Workflow YAML shape
- opt-in `argo lint` and `argo submit --dry-run`
- Dagster definition loading
- optional Dagster asset materialization

It can also repair deterministic bundle-layout issues without rewriting node scripts:

- create missing `inputs/`, `nodes/`, and `outputs/` directories
- normalize `inputs/input_manifest.json`
- create missing per-node output placeholders
- normalize `bundle-manifest.json`
- restore root and Dagster Docker Compose files
- normalize Dagster `defs.yaml` script and manifest paths

## Quick CLI

```bash
python -m venv .venv
.venv/bin/pip install -e .
.venv/bin/python -m app.validator \
  /path/to/inlumen-argo-dagster-artifacts
```

You can also pass a generated `dagster/`, `dagster_project/`, or Argo YAML path.

After the first install, reuse the generated project's validation venv for faster checks:

```bash
.venv/bin/python -m app.validator \
  /path/to/inlumen-argo-dagster-artifacts \
  --skip-install
```

## API

```bash
.venv/bin/uvicorn app.main:app --host 127.0.0.1 --port 8020
curl -X POST http://127.0.0.1:8020/validate \
  -H 'Content-Type: application/json' \
  -d '{"bundle_path":"/path/to/exported-bundle","targets":{"argo":true,"dagster":true},"materialize":true}'

curl -X POST http://127.0.0.1:8020/validate-and-repair \
  -H 'Content-Type: application/json' \
  -d '{"bundle_path":"/path/to/exported-bundle","targets":{"argo":true,"dagster":true},"materialize":true}'
```

When the InLumen backend runs in Docker, the backend and validation service must agree on the mounted bundle path. Configure the backend path mapping with:

```env
INLUMEN_DEPLOYMENT_VALIDATION_LOCAL_ROOT=/path/inside/backend/container
INLUMEN_DEPLOYMENT_VALIDATION_REMOTE_ROOT=/path/inside/validation/container
```

The backend writes a generated bundle under its validation work directory, rewrites that path into the validation container's view, and sends the rewritten path to `/validate` or `/validate-and-repair`.

The validator intentionally uses an isolated virtualenv inside the generated Dagster project. This catches packaging errors, Dagster definition load errors, and runtime handoff errors between generated node scripts. Argo CLI checks are opt-in because many local `argo lint`/dry-run paths require an active Kubernetes/Argo context.
